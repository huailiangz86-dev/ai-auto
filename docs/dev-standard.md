## 1. 规范目的

本规范定义 AI auto 项目全生命周期开发流程，确保：

- **PRD → Story → UI → 开发 → 测试** 全链路可追溯
- 各端（API / 商家后台 / 分享员后台 / C端小程序 / 运营后台）代码质量一致
- 新需求必须经过评审才能执行，杜绝"接到指令直接开写"的情况
- 单元测试是代码交付的硬性标准，不可绕过
- 每一次新需求必须经过确认才能执行

---

## 2. 铁律（不可违反）

> **执行前必须问我确认。没有确认不执行任何需求。**

这条规则适用于：

- 新功能的代码实现
- 现有功能的改动
- 数据库结构变更
- 外部集成改动
- 设计变更

询问方式：

```
[新需求] 您希望我执行 {需求描述} 吗？
        预计影响：{简述}
        执行前请回复"确认执行"
```

## 3. 开发流程规范

### 3.1 标准开发流程（需求 → 上线）

```
┌─────────────────────────────────────────────────────────┐
│  阶段 1：需求确认                                        │
│  用户提出需求 → 评估范围 → 确认执行                       │
│  ⚠️ 不确认不进入下一阶段                                 │
├─────────────────────────────────────────────────────────┤
│  阶段 2：PRD 评审                                       │
│  功能描述 / 业务规则 / 验收标准                        │
│  ⚠️ 关键需求新增/修改必须更新 PRD                       │
├─────────────────────────────────────────────────────────┤
│  阶段 3：用户故事拆分                                   │
│  按 Epic → Story 拆分，每个 Story 有验收标准            │
│  ⚠️ Story 数量和估算需经评审                            │
├─────────────────────────────────────────────────────────┤
│  阶段 4：UI 设计评审                                    │
│  页面流程 / 组件规范 / 交互细节                         │
│  ⚠️ 新界面或改版必须输出 UI 设计文档                     │
├─────────────────────────────────────────────────────────┤
│  阶段 5：API 契约评审                                   │
│  接口定义 / 请求响应格式 / 错误码                        │
│  ⚠️ 前后端联调前必须完成                                │
├─────────────────────────────────────────────────────────┤
│  阶段 6：编码实现                                       │
│  单元测试 → 功能代码 → 代码评审                         │
│  ⚠️ 单元测试覆盖率 ≥ 80%，未通过不合并                  │
├─────────────────────────────────────────────────────────┤
│  阶段 7：集成验证                                       │
│  API 联调 → 端到端测试 → 部署验证                       │
│  ⚠️ 所有 Story 验收通过才能提测                          │
└─────────────────────────────────────────────────────────┘
```

### 3.2 流程简化规则

| 场景             | 可简化的阶段        | 说明                      |
| ---------------- | ------------------- | ------------------------- |
| Bug 修复（小）   | UI/PRD 可跳过       | 不影响已有功能的 bug 修复 |
| 配置调整         | UI/PRD/Story 可跳过 | 环境变量、配置项调整      |
| 已有功能小幅优化 | PRD 可跳过          | 不改变业务逻辑的体验优化  |
| 新功能开发       | 无简化              | 所有阶段必须完整执行      |

## 4. 各端开发标准

每个子平台必须遵循对应的开发标准：

| 子平台         | 技术栈              | 文档        | 测试要求                  |
| -------------- | ------------------- | ----------- | ------------------------- |
| **Core API**   | NestJS + TypeScript | API 契约    | 服务层 + 业务逻辑单元测试 |
| **AI Agent**   | Python + FastAPI    | API 契约    | 核心算法单元测试          |
| **商家后台**   | React + Ant Design  | UI 设计文档 | 组件测试 + API 集成测试   |
| **分享员后台** | React（移动端优先） | UI 设计文档 | 组件测试 + API 集成测试   |
| **C端小程序**  | Uni-app（微信）     | UI 设计文档 | 组件测试 + 页面集成测试   |
| **运营后台**   | React + Ant Design  | UI 设计文档 | 组件测试 + API 集成测试   |

详见各端开发标准文档：

- [Core API 开发标准](core-api-dev-standard.md)
- [小程序开发标准](miniapp-dev-standard.md)
- [Web 后台开发标准](web-backend-dev-standard.md)

## 5. 文档管理规范

### 5.1 文档清单

| 文档        | 位置                             | 更新时机                     |
| ----------- | -------------------------------- | ---------------------------- |
| PRD         | `docs/prd-*.md`                  | 新 Epic / 业务规则变更时更新 |
| 架构文档    | `docs/architecture-*.md`         | 新组件 / 数据模型变更时更新  |
| Sprint 计划 | `docs/sprint-plan-*.md`          | 新 Story 拆解时更新          |
| UI 设计     | `docs/design/*.md`               | 新界面 / 改版时更新          |
| API 契约    | `docs/api-contract-*.md`         | 新接口 / 接口变更时更新      |
| 代码规范    | `docs/dev-standard.md`（本文件） | 规范变更时更新               |

### 5.2 文档评审要求

- **PRD 变更**：必须经过评审，变更内容需在 PRD 顶部 changelog 记录
- **API 契约**：前后端各一名代表参与评审
- **UI 设计**：产品 + 开发 + 设计三方评审
- **架构变更**：技术负责人评审，重大变更需全员通知

## 6. 代码质量规范

### 6.1 单元测试（强制要求）

| 类型                  | 覆盖率要求   | 强制执行 |
| --------------------- | ------------ | -------- |
| Core API 服务层       | ≥ 80%        | ✅ 必须  |
| AI Agent 核心算法     | ≥ 80%        | ✅ 必须  |
| 业务计算（佣金/归属） | 100%         | ✅ 必须  |
| React 组件            | 关键交互覆盖 | ✅ 必须  |
| React Hooks           | 逻辑覆盖     | ✅ 必须  |

**测试禁止事项：**

- ❌ 不能 mock 内部实现细节
- ❌ 不能只测试 happy path
- ❌ 不能用 `console.log` 替代断言
- ❌ 不能跳过 CI 失败强行合并

### 6.2 代码评审（强制要求）

- 所有 PR 必须经过代码评审才能合并
- 评审维度：功能正确性 / 性能 / 安全性 / 可维护性
- 高风险改动（支付/佣金/权限）：至少 2 人评审

## 7. 版本与分支管理

### 7.1 分支命名

```
feature/STORY-{ID}-{short-title}   # 功能开发
bugfix/{description}                 # Bug 修复
hotfix/{description}                # 紧急修复
chore/{description}                 # 工具/依赖更新
docs/{description}                   # 文档更新
```

### 7.2 Commit 规范

```
feat(core): add commission calculation service (STORY-007)

- Add calculateCommissionWithLevel() with level multiplier support
- Add unit tests for bronze/silver/gold/diamond/king levels
- Fix floating point precision issue in fee calculation

Closes STORY-007
```

### 7.3 PR 规范

每个 PR 必须包含：

- 关联的 Story ID
- 变更描述
- 测试结果截图
- 部署/迁移说明（如有）

---

## 8. 安全红线

以下操作禁止在未确认的情况下执行：

- ❌ 删除数据库表或字段
- ❌ 修改佣金计算逻辑
- ❌ 改动权限控制
- ❌ 修改第三方集成（支付/OAuth/短信）
- ❌ 提交 secrets / keys 到仓库
- ❌ 修改生产环境配置
